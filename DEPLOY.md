# Deploying EvalSuite on free services

Everything below has a free plan that needs no credit card (checked October 2026; providers change their
limits, so confirm on their pricing pages).

| Part                    | Service                     | Free plan highlights                                                   | Limitation to know                                                |
| ----------------------- | --------------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Website (Next.js)       | **Vercel** Hobby            | Automatic HTTPS, deploys from GitHub or GitLab, `*.vercel.app` address | Non-commercial use only                                           |
| API (FastAPI, Docker)   | **Render** free web service | 512 MB RAM, HTTPS, deploys from Git, `*.onrender.com` address          | Sleeps after 15 min idle; first request then takes about a minute |
| PostgreSQL              | **Neon** free               | 0.5 GB storage, always-on branch                                       | Compute pauses when idle (wakes in about a second)                |
| Redis (rate limits)     | **Upstash** free            | TLS Redis, daily command quota                                         | Quota is ample for this site                                      |
| Email (resets, notices) | **Brevo** free              | 300 emails per day over SMTP                                           | Sender address must be verified                                   |

Order matters: create the database, Redis and email first, then the API, then the website.

---

## 1. Put the code in a Git repository

Push the project to GitHub (or GitLab; both Render and Vercel connect to either). Do not commit `.env`
files; they are already in `.gitignore`.

## 2. PostgreSQL on Neon

1. Sign up at neon.tech and create a project (region close to your users, for example Singapore or Frankfurt).
2. Open **Connection details**, turn **Connection pooling off**, and copy the connection string. It looks like
   `postgresql://user:password@ep-xxxx.region.aws.neon.tech/neondb?sslmode=require`.
   Use the direct (non-pooled) string: database migrations need it.
3. Keep it for step 5 as `EVALSUITE_DATABASE_URL`.

## 3. Redis on Upstash

1. Sign up at upstash.com and create a Redis database (TLS on, same region as Neon if possible).
2. Copy the **Redis URL** starting with `rediss://` (two s: TLS), for example
   `rediss://default:password@xxxx.upstash.io:6379`.
3. Keep it for step 5 as `EVALSUITE_REDIS_URL`.

## 4. Email on Brevo

1. Sign up at brevo.com, then **Senders, domains and dedicated IPs → Senders** and verify the address emails
   should come from (for example your personal Gmail).
2. **SMTP & API → SMTP**: note the login (your SMTP username) and create an SMTP key (the password).
3. Keep them for step 5.

## 5. API on Render

1. Sign up at render.com with your Git provider.
2. **New → Blueprint**, pick the repository. Render reads `render.yaml` and proposes the `evalsuite-api` service.
3. Fill the values it asks for:

   | Variable                  | Value                                                                                                               |
   | ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
   | `EVALSUITE_DATABASE_URL`  | Neon string from step 2                                                                                             |
   | `EVALSUITE_REDIS_URL`     | Upstash `rediss://` URL from step 3                                                                                 |
   | `EVALSUITE_SITE_URL`      | The website address, for example `https://evalsuite.vercel.app` (pick the name now; you can change it after step 6) |
   | `EVALSUITE_CORS_ORIGINS`  | `["https://evalsuite.vercel.app"]` (JSON list, same address)                                                        |
   | `EVALSUITE_SMTP_USERNAME` | Brevo SMTP login                                                                                                    |
   | `EVALSUITE_SMTP_PASSWORD` | Brevo SMTP key                                                                                                      |
   | `EVALSUITE_EMAIL_FROM`    | `EvalSuite <the-verified-address@gmail.com>`                                                                        |

   The three secrets (`EVALSUITE_JWT_SECRET`, `EVALSUITE_API_KEY_PEPPER`, `EVALSUITE_DOWNLOAD_TOKEN_SECRET`) are
   generated by Render automatically.

4. Click **Apply**. The first build takes a few minutes. On start the container runs the database migrations,
   then the server. Production mode refuses to start if a required setting is missing, and the log says which.
5. When it is live, open `https://<your-api>.onrender.com/api/v1/health/ready`. You should see
   `{"status":"ok","database":true,"rateLimitStore":true}`.
6. Open the service's **Environment** tab and copy the generated `EVALSUITE_DOWNLOAD_TOKEN_SECRET` for step 6.

## 6. Website on Vercel

1. Sign up at vercel.com with your Git provider, **Add New → Project**, import the repository.
2. Framework preset: **Next.js** (detected). Root directory: the repository root. Leave build settings as they are.
3. Environment variables (Production):

   | Variable                     | Value                                                                           |
   | ---------------------------- | ------------------------------------------------------------------------------- |
   | `NEXT_PUBLIC_SITE_URL`       | `https://evalsuite.vercel.app` (your project address)                           |
   | `NEXT_PUBLIC_API_BASE_URL`   | `https://<your-api>.onrender.com`                                               |
   | `DOWNLOAD_TOKEN_SECRET`      | The value copied in step 5.6 (server-only; never prefix it with `NEXT_PUBLIC_`) |
   | `NEXT_PUBLIC_REPOSITORY_URL` | Optional: your public repository address                                        |
   | `NEXT_PUBLIC_PYPI_URL`       | Leave empty until EvalSuite is on PyPI                                          |

4. **Deploy**. `NEXT_PUBLIC_*` values are built into the pages, so redeploy whenever you change them.
5. If the final address differs from what you entered in step 5, update `EVALSUITE_SITE_URL` and
   `EVALSUITE_CORS_ORIGINS` on Render (it redeploys automatically).

## 7. Check the deployment

```bash
SITE_URL=https://evalsuite.vercel.app API_BASE_URL=https://<your-api>.onrender.com npm run check:deploy
```

It waits for the API to wake up, then checks HTTPS, the database and Redis, CORS, authentication, the
visitor counter, every main page, and that release files are not publicly reachable. It is read-only.
Then try the site yourself: register with a personal email, create an API key, run the playground on the API,
and request a password reset to confirm email delivery.

## 8. Optional: keep the API awake

Free Render services sleep after 15 minutes without traffic. `.github/workflows/keep-warm.yml` pings the API
every 14 minutes from 03:00 to 18:59 UTC (08:30 to 00:29 IST). Enable it by adding a repository **variable**
`API_BASE_URL` (GitHub: Settings → Secrets and variables → Actions → Variables). It stays within Render's 750
free instance-hours per month for one service.

## Troubleshooting

**"An internal error occurred" or "temporarily unavailable"**, with `NoPermissionError` or `NOPERM` in
Render's logs: `EVALSUITE_REDIS_URL` uses Upstash's read-only user. Copy the read-write URL (user `default`,
not `default_ro`) and redeploy. `/api/v1/health/ready` reports `"rateLimitStore": false` until it is fixed.

**Emails do not arrive** (reset links, "Notify me" confirmations). Render's **Logs** show
`Email delivery failed: <error>`. Free hosts often block SMTP ports 587 and 465. Either set
`EVALSUITE_SMTP_PORT` to `2525` (Brevo accepts it), or switch to Brevo's HTTPS API: create a key under
**Brevo → SMTP & API → API Keys**, then set `EVALSUITE_EMAIL_BACKEND=brevo` and `EVALSUITE_BREVO_API_KEY`. In
both cases `EVALSUITE_EMAIL_FROM` must be a verified Brevo sender. Delivery failures never block the request
itself: the sign-up or reset request is still saved.

**"Could not reach the EvalSuite API"** (sign-in, download email step, playground on the API):

1. Open `https://<your-api>.onrender.com/api/v1/health/ready` in a browser.
   - It loads slowly, then shows `"status":"ok"`: the API was asleep. Try the site again.
   - Render shows an error page or the service is "Failed" in the dashboard: open **Logs**. Production mode
     prints exactly which setting is missing (for example `EVALSUITE_SMTP_HOST` or a secret).
   - `"database":false` or `"rateLimitStore":false`: check `EVALSUITE_DATABASE_URL` (Neon direct string) or
     `EVALSUITE_REDIS_URL` (read-write `rediss://default:...`, not `default_ro`).
2. Check the address in your browser's address bar. It must be listed **exactly** in `EVALSUITE_CORS_ORIGINS`
   (scheme, no trailing slash), for example `["https://evalsuite-mkcs28.vercel.app"]`. Vercel also serves each
   deployment at addresses like `evalsuite-abc123-mkcs.vercel.app`; to allow those, set
   `EVALSUITE_CORS_ORIGIN_REGEX` to `^https://evalsuite-[a-z0-9-]+-mkcs\.vercel\.app$`.
3. On Vercel, `NEXT_PUBLIC_API_BASE_URL` must be the API address with `https://` and no path. It is built into
   the pages: after changing it, **redeploy**.
4. Run `npm run check:deploy` (section 7); it reports which of these is wrong.

## Updating

Push to the main branch: Vercel and Render redeploy automatically, and the API applies any new database
migrations on start. Publishing a package release (`npm run release:add`) is a normal commit and deploys the
same way.

## Moving off the free tier later

Nothing is tied to these providers: the API is a standard Docker image (`backend/Dockerfile`) that reads
`PORT`, and the website is a standard Next.js app (or the root `Dockerfile`). Paid plans of the same services,
or any VPS running `docker compose up`, work without code changes.
